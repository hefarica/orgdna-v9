# OrgDNA V6: fuentes, diseño y mejora con evidencia

Esta entrega actualiza la aplicación sobre los bytes entregados en V5. Conserva el snapshot base de 24 agentes, sus IDs, ADN, prompts, JSON importables, fechas de exportación y plantilla Excel sin regenerarlos. El catálogo documental y el manifiesto SHA-256 se recalculan para los archivos actualizados. Las correcciones V5 de modelos, alcance del catálogo y diagnóstico de generación siguen formando parte de la aplicación.

## Inventario GitHub

La resolución de una referencia solicita su SHA sin descargar el diff del commit. La metadata del árbol se obtiene para ese commit fijado. Un árbol recursivo truncado, superior a 3 MB o a 5.000 entradas activa el recorrido por subárboles no recursivos, también fijados a SHA. No se usa paginación del endpoint tree ni se interpreta `recursive=0` como una solicitud no recursiva.

El recorrido está acotado: 24 solicitudes de árboles incluyendo el intento recursivo, 12 MB acumulados, profundidad 16, 5.000 entradas y un presupuesto temporal de 120 segundos para planificación y timeouts. Un subárbol individual demasiado grande puede quedar sin inventariar; los gaps y presupuestos se reflejan en cobertura. Los límites HTTP y de contenido por archivo no se elevan para fingir una lectura completa. Se omiten blobs binarios o conocidos como demasiado grandes antes de descargarlos y se verifica el SHA de Git del contenido recibido.

La caché local LRU puede reutilizar inventarios completos por repositorio, SHA de árbol, versión de política y límites/perfil de lectura. La rama se resuelve de nuevo en cada análisis; inventarios parciales y errores no se almacenan. Comparte un límite por defecto de 2 MB y 256 entradas con los blobs y se puede vaciar. La procedencia diferencia el árbol reutilizado de la lectura de red; muestra aciertos, solicitudes, tiempo observado y bytes de respuesta observables. No incluye headers ni bytes que el transporte no pueda medir tras una excepción. Los misses simultáneos pueden duplicar solicitudes; no hay garantía de latencia ni de captura remota atómica.

## Evidencia de sitios web

La aplicación admite una fuente web pública HTTPS con lectura acotada de HTML, separada de un repositorio GitHub. Extrae evidencia textual y elementos observables de la interfaz, conservando procedencia y límites. No inicia sesión, no ejecuta JavaScript ni renderiza una SPA en navegador; no envía formularios ni activa controles. Una página que dependa de JavaScript puede ofrecer evidencia insuficiente. No se presenta como lectura del 100% del sitio ni como captura remota atómica.

Los valores por defecto son 12 páginas, 600 KB de contenido, profundidad 2, 30 solicitudes, 30 segundos de planificación y hasta 4 lecturas paralelas. El límite por página es 150 KB y se adapta al presupuesto disponible. El lector respeta robots y limita enlaces al mismo origen; un error al consultar robots bloquea la lectura salvo la ausencia explícita 404/410. La caché es acotada, con TTL de 300 segundos, y vuelve a comprobar robots. Los snapshots registran URL, SHA-256 y fecha de lectura, sin afirmar atomicidad remota. La cobertura web se marca siempre parcial.

## Diseño de equipos nuevos

Las generaciones nuevas, o un reinicio explícito del diseño, incorporan jerarquía por afinidad funcional, diferenciación entre perfiles y propuestas de subequipos. Las propuestas no crean equipos activos en DSH. La jerarquía histórica y las modificaciones manuales se conservan; no se reconstruye el equipo incluido para imponer el algoritmo nuevo.

Las recomendaciones de herramientas se vinculan al ID del agente actual. Los diseños nuevos incorporan motivos por herramienta, distinción entre candidato y permiso concedido, y advertencias sobre amplitud. No acreditan que las herramientas estén disponibles en el runtime. Los bloqueos y permisos manuales no se convierten automáticamente en una allowlist nueva.

## Evaluación local y mejora

La evaluación local se inicia a demanda tras revisar y autorizar un plan: comando exacto, carpeta, huella de fuentes y referencias de ejecución y agentes. Hay tres perfiles cerrados: `python_unittest_v1`, `python_pytest_v1` y `node_test_v1`. Unittest usa el Python de la aplicación en modo aislado `-I -B` con un harness fijo, carpeta de tests revisada y patrón `test*.py`; no requiere dependencias externas. Pytest exige que pytest ya esté instalado en ese Python; si falta, se bloquea sin instalarlo. Pytest no se ejecutó en el entorno QA por faltar esa dependencia. Node requiere un ejecutable local de Node, resuelto a ruta absoluta y huella, y ejecuta `--test --test-reporter=tap` sobre una lista explícita de hasta 100 archivos compatibles. Python y Node fueron probados con fixtures reales en Linux. Las unidades TAP de Node pueden representar un archivo sin assertions; el resultado distingue `execution_unit` y no debe interpretarse cada unidad como una prueba funcional completa. No se instala software ni se ejecuta un comando de shell arbitrario. Los tests del proyecto siguen siendo código ejecutable: la selección de comandos y el control del entorno no equivalen a un sandbox de seguridad. No ejecutes pruebas de código no confiable. Los resultados proceden del proceso de tests y se etiquetan como no confiables; las assertions no se verifican de forma independiente. Un resumen sin errores no prueba por sí solo la calidad del proyecto. El snapshot admite como máximo 10.000 archivos, 100 MB totales y 20 MB por archivo, sin symlinks. El tiempo de ejecución es de 1 a 120 segundos y la captura está acotada a 1.024–262.144 bytes. Los logs crudos no se incluyen en el contenido mostrado o enviado; el entorno no hereda API keys. La terminación por grupo de procesos fue probada en Linux; el mecanismo Windows JobObject está implementado pero no se ha probado en Windows.

La propuesta de mejora puede usar resultados reales vinculados a la misma organización y versión, con huella de la fuente local evaluada. El manifiesto local no equivale al SHA de un commit Git: no se acredita automáticamente identidad entre el árbol local evaluado y un repositorio remoto. Transmitir evidencia al proveedor sigue requiriendo la aprobación AI correspondiente. No hay llamadas de pago automáticas. La vista previa muestra las ejecuciones, agentes, métricas y objetivos de mejora sin logs ni argumentos crudos. El resultado es un diff antes/después propuesto revisable y un plan de repetir pruebas; no acredita por sí solo skills verificadas ni una instalación o activación en DSH. Los límites y pruebas efectivamente realizadas se detallan en el informe QA.

## Biblioteca y recomendaciones de capacidades

La biblioteca local persistente almacena referencias y asignaciones en SQLite, sin credenciales ni concesiones de permisos. Las versiones históricas del mismo proyecto consultan su biblioteca viva y muestran ese aviso; no se presentan como snapshots históricos de la biblioteca. Guardar como otro proyecto crea una copia independiente de su namespace y conserva la procedencia del fork. La paginación permite 1–200 registros por página; no existe un límite total de 500 registros. La cuota lógica por proyecto es 256 MiB, con solicitudes de hasta 2 MiB e ítems de hasta 128 KiB. El contexto activo tiene un presupuesto por defecto de 12 KB y máximo de 24 KB: no se inyecta toda la biblioteca a cada agente ni se corta contenido para fingir que cabe.

Las asignaciones en lote son revisables y distinguen asignado, activo, instalado y verificado. Sólo las instrucciones y políticas de memoria activadas explícitamente pueden compilarse en el prompt exportado, completas y dentro del presupuesto; plugins y conectores no se convierten en instrucciones activas. El manifiesto vincula el companion y los prompts por huella e informa qué ítems entraron o se aplazaron. Desactivar o quitar contexto recalcula desde el prompt base, sin residuos; no cambia IDs, modelos ni permisos. La identidad operativa de los diseños nuevos describe rol, misión y coordinación de un agente de IA, sin impersonar una persona ni inventar recuerdos. Tener una referencia no instala un plugin, no concede acceso a Gmail o llamadas ni autoriza una acción externa. La propuesta determinista funciona sin API key. La recomendación AI prepara una vista previa con proveedor, modelo API, endpoint, catálogo y organización fijados por huella; los candidatos se limitan a IDs conocidos. Requiere autorización específica y usa un máximo de 32 agentes, 64 candidatos, lotes de 8 y 4 llamadas, sin reintentos o fallback automáticos. Una propuesta incompleta no se convierte en una asignación parcial silenciosa.

Una referencia pública puede leerse para preparar una propuesta revisable: HTTPS estático sin JavaScript, respetando robots y sin caché, o README/SKILL.md de GitHub público con commit fijado y verificación del blob. Por defecto lee una página, hasta 300.000 bytes y 6.000 caracteres de extracto; los máximos son cinco páginas, 1 MB y 12.000 caracteres. Las URLs no admiten query, fragmento, credenciales ni destinos locales. Leer una referencia no importa ni ejecuta su contenido. Los paquetes siguen requiriendo un catálogo verificado; una página web no acredita que un plugin sea legítimo o esté instalado.

## Companion de capacidades para DSH

Cuando el proyecto posee una biblioteca real, el add-on puede incorporar un manifiesto companion versionado con su huella de configuración. El snapshot histórico de 24 agentes no recibe capacidades inventadas. Los scripts de preflight revisan el manifiesto y el namespace esperado; no sustituyen una instalación ni acreditan un import en DSH real. El export de la aplicación incluye el companion por separado y lo vincula por SHA-256 al manifiesto, sin campos adicionales incompatibles en las raíces DSH. La publicación local es por namespace y versión propios, con preview, verificación y rollback limitado a los archivos publicados que no hayan cambiado. Los deltas conservan los IDs y usan comparación de versión/huella antes de aplicar; requieren una solicitud de recarga separada y comprobación posterior de su ID y huella destino. El protocolo escribe un recibo propio y permite al runtime recargar el snapshot en memoria; no se presenta como hot-update confirmado en un DSH real. Los perfiles e importables históricos conservan sus bytes. La carga de capacidades no significa que un agente pueda usar herramientas no conectadas, actuar como una persona ni saltarse aprobaciones.

## Workflow por recurso

Una referencia revisada puede convertirse en propuestas para roles concretos: lectura pública o snapshot de investigación, evidencia visible, propuesta determinista o recomendación AI bajo aprobación exacta, selección de un subconjunto y preview antes de asignar o activar contexto local. La aplicación no instala el recurso por leerlo ni transforma una propuesta en autoridad de ejecución.

DataInventor aparece como referencia de investigación para generación de datos sintéticos. La envoltura pública y un backend enlazado son evidencias distintas; no se ha verificado aquí un contrato API funcional, instalación, modelos, precios ni ejecución del backend. Los workflows derivados son propuestas basadas en ese alcance, no un endpoint DataInventor instalado o probado. Datos sintéticos tampoco se convierten por sí solos en evaluación canónica.

## Asistente de conexión DSH

El harness coordina el relanzador existente y una conexión efímera de lectura. Prepara un plan exacto con huella, ejecutable, argumentos, puertos y backup; el inicio requiere confirmaciones explícitas y sólo admite reutilización. Si ya existe un listener no inicia otra instancia. Un puerto TCP abierto no acredita identidad ni autenticación. El inicio aprobado utiliza el relanzador original una sola vez y espera dentro de un plazo acotado, sin matar procesos al expirar.

Activar el add-on y proporcionar el código efímero de pairing son pasos nativos separados. La comprobación autenticada compara dos lecturas del roster y, cuando se proporciona, su huella esperada. `READ_ONLY_VERIFIED` sólo acredita esa lectura estable; no demuestra ejecución de tareas, identidad completa de sesión, disponibilidad de modelos o compatibilidad total de plugins. Sin huella esperada no acredita que el roster observado sea la organización elegida.

No se instala DSH, no se cambian perfiles/configuración, no se crean credenciales persistentes ni se declara una instalación real verificada. Los tests del harness usan dobles inertes y servicios mock en loopback; no ejecutan el EXE entregado ni prueban el arranque en Windows o la preservación de sesiones reales. Los requisitos de carga de overlay/PluginManager y su aprobación deben verificarse en el runtime instalado; ver `engine/DSH_HARNESS_CONTRACT.md`.

## Uso y verificación

Revisa la fuente, la cobertura y el contenido preparado antes de autorizar su transmisión al proveedor de AI. Una lectura parcial no equivale a un inventario completo. Las comprobaciones realizadas y sus límites figuran en `qa_multifuente_v6.md`.

Para actualizar conservando los proyectos guardados, sigue `actualizar_sin_perder_proyectos.md`: copiar únicamente `data/projects` y no copiar API keys ni credenciales. No se ha ejecutado esta actualización en el equipo del usuario ni se ha demostrado un import real en DSH, Excel COM o Windows mediante las pruebas offline.
